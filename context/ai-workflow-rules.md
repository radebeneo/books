# AI Workflow Rules

## Approach

Build this project incrementally using a spec-driven workflow.
The six files in `context/` define what to build, how to build
it, and the current state of progress.

Before writing any code:

1. Read `context/progress-tracker.md` to understand the current
   phase, what is complete, and what the current goal is.
2. Read the relevant section of `context/architecture.md` to
   confirm which folder owns the code you are about to write.
3. Read `context/code-standards.md` to confirm the patterns you
   must follow before touching any file.

Do not infer behavior from the existing code alone. Implement
against the context files. If the context files and the code
disagree, flag the discrepancy — do not silently pick one.

---

## Scoping Rules

- Work on exactly one feature unit at a time. A unit is the
  smallest piece of work that can be verified end to end.
- Do not write speculative code for a future unit while
  implementing the current one.
- Do not refactor code that is unrelated to the current unit.
  If you spot a problem, add it to `Open Questions` in
  `progress-tracker.md` and continue.
- Do not add npm packages without explicitly stating what
  package is needed, what it does, and why it is required.
  Wait for approval before installing.
- Do not modify environment variables or `.env.local`. If a
  new variable is needed, list it in `progress-tracker.md`
  under Session Notes and stop.

---

## When to Split Work

Split an implementation step into two or more steps if it
combines any of the following:

- A Server Action change and a UI component change that are
  not directly wired to each other in the same unit
- Changes to more than one Mongoose model
- A new API route and a new Server Action
- Any change to `app/globals.css` (design system) combined
  with a feature implementation
- Behavior that is not fully defined in `project-overview.md`
  or `architecture.md`

If completing a unit requires more than one `npm run build`
verification cycle, the scope is too large. Split it.

## Handling Missing Requirements

When a required behavior is not defined in any context file:

1. Stop. Do not guess or invent the behavior.
2. Add the unresolved question to `## Open Questions` in
   `context/progress-tracker.md`. Write it as a specific
   question, not a vague note.
3. Return the question to the user with a one-sentence
   explanation of why it blocks progress.
4. Do not proceed with implementation until the question is
   resolved and the answer is written into the relevant
   context file.

When a requirement exists but is ambiguous:

1. State the two or more interpretations explicitly.
2. Recommend one interpretation and explain why.
3. Ask the user to confirm before implementing.

Never implement the most lenient interpretation to avoid
asking. Ask.

## Protected Files

Do not modify the following files under any circumstances
unless the user gives an explicit instruction to do so:

- `components/ui/button.tsx`
- `components/ui/form.tsx`
- `components/ui/input.tsx`
- `components/ui/label.tsx`
- `components/ui/radio-group.tsx`
- `components/ui/sonner.tsx`

These are generated shadcn/ui primitives. They may be
regenerated by `npx shadcn add` at any time. Application-
specific changes added to these files will be overwritten.
Extend them with wrapper components in `components/` instead.

Do not modify the following files unless fixing a direct
build error caused by your own change:

- `next.config.ts`
- `tsconfig.json`
- `postcss.config.mjs`
- `eslint.config.mjs`
- `.env.local`
- `package.json` (unless adding an approved dependency)
- `package-lock.json` (never edit directly)

## Keeping Docs in Sync

After completing any unit, update `context/progress-tracker.md`
before stopping. Move completed items to `## Completed`, update
`## Current Goal`, and populate `## Next Up` with the next unit.

Update the relevant context file immediately — not at the end
of the session — when any of the following change:

| What changed | Which file to update |
| --- | --- |
| A new folder is created or responsibility shifts | `architecture.md` — System Boundaries |
| A new collection, index, or field is added to MongoDB | `architecture.md` — Storage Model |
| A new constant, voice option, or config value is added | Note it in `progress-tracker.md` — Architecture Decisions |
| A new coding pattern is established | `code-standards.md` — relevant section |
| A new page or API route is created | `architecture.md` — System Boundaries; add route to `Navbar.tsx` navItems if it needs a nav link |
| An open question is resolved | Remove it from `progress-tracker.md` — Open Questions; write the decision into the relevant context file |
| Scope changes (something added or removed) | `project-overview.md` — In Scope / Out of Scope |

Do not let the context files drift from the implementation.
A context file that does not match the code is worse than no
context file.

## Verification Checklist

Complete every item on this checklist before marking a unit
done and moving to the next one.

1. **End-to-end test**: The feature works in the browser from
   the user's entry point to the expected outcome. Test it
   manually or describe the exact steps to do so.
2. **No invariant violated**: Check every invariant in
   `context/architecture.md` — `## Invariants`. Confirm none
   were broken by the change.
3. **No unrelated files modified**: The diff contains only
   files that are directly part of the current unit.
4. **TypeScript clean**: Run `npm run lint`. Zero errors, zero
   warnings related to your changes.
5. **Build passes**: Run `npm run build`. It must complete
   with no TypeScript errors and no ESLint errors.
6. **`progress-tracker.md` updated**: The completed unit is
   in `## Completed`. `## Current Goal` reflects the next
   unit. `## Session Notes` contains anything a future agent
   needs to resume without re-reading the entire codebase.
7. **No orphaned data**: If the unit writes to MongoDB, verify
   that a failure path does not leave orphaned documents. The
   rollback pattern from `saveBookSegments()` is the model.
8. **Clerk auth guard in place**: If the unit introduces a new
   Server Action or API route that mutates data, confirm that
   `auth()` is called at the top and the handler returns early
   if `userId` is null.
9. **`serializeData()` called**: If the unit returns a Mongoose
   document from a Server Action to a client component, confirm
   `serializeData()` wraps the document before it is returned.
10. **No new hardcoded values**: Brand hex values use Tailwind
    inline notation or CSS variables. Voice IDs come from
    `voiceOptions` in `lib/constants.ts`. File size limits come
    from `MAX_FILE_SIZE` / `MAX_IMAGE_SIZE` in `lib/constants.ts`.

If any item fails, fix it before moving on. Do not carry
failures forward to the next unit.
